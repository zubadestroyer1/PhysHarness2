# Deep runtime and context audit (read only)

This audit uses the immutable `manifest.json` and SHA named payloads in the calibration, first cooperative, and cooperative retry exports. It examines visible calls, results, events, and checkpoint metadata. It does not decode or infer private reasoning. Counts below are from the latest native checkpoint per session, plus all exported runtime events. Cumulative token numbers are provider usage, not unique context size.

## Highest impact: full state checkpoint amplification

The retry records 2,087 `native_checkpoint` artifacts for 338 provider `usage` events, or 6.17 checkpoints per response. The six final states contain, respectively, 90/89, 86/85, 42/41, 49/48, 59/58, and 12/11 responses/tool results. Initial checkpoints are roughly 15–20 KB; final ones reach 3,210,868, 3,098,426, 1,516,146, 1,615,997, 1,998,348, and 478,620 bytes. This is an observable whole-state repetition: `ResponsesRuntime.start` initializes growing `input` and `responses` arrays (`src/physharness/execution/responses.py:258`); each provider response appends both the native response and its output, with saves around accounting (`:730–767`); `CanonicalRuntimeStore._save_checkpoint` serializes the complete checkpoint to an immutable artifact (`src/physharness/orchestration/research_worker.py:134–147`). The exporter therefore retains many successive snapshots of almost identical prefixes. Root's byte-level export accounting gives 2,504,180,069 native-checkpoint payload bytes of 2,504,754,798 unique payload bytes in the retry (>99.97%). This is a storage/export scalability issue, not evidence of model context overflow or VM RSS usage. Preserve safety boundaries and immutable recovery semantics if considering incremental/delta or chunked content-addressed snapshots; reducing checkpoint frequency would trade away durability.

The first cooperative run likewise has 1,723 native checkpoints across 280 provider responses. One session (`f2f8f96b-9907-44b4-8519-e8bda23cb734`) has 735 checkpoints despite only six responses in its **post-compaction** active history; it had a longer prior epoch. The `compaction` event `7ccb7649-0295-4a7f-8a53-32d8def9dcef` at 2026-09-24 23:28:09 UTC reports 333 active items before and five after, with matching `provider_compaction_items` event `c35ddf73-3d51-4d6c-8fb8-83d98f366d52`. Its cumulative session input is 9,449,034 tokens while its six retained responses each used 59,905–76,249 input tokens. That is consistent with cumulative accounting surviving active-context pruning, not a 9.4-million-token single prompt. After compaction, the agent called `submit_candidate`, waited for verification twice, messaged peers twice, and produced a final response. Its mapped task `b799ba49-bf91-45dd-99f2-70f9619ac19d` is `completed` (native session `f2f8f96b...` maps through session record `87d8ffb5...`); a different first-cooperative root became blocked/uncertain, affecting the overall workflow. The first-cooperative manifest also preserves verified receipt `64a21308-8c8a-4624-a82e-cc87354e3f92` and verified claim `3f956c22-63af-44b7-a525-b6772f33e1b5`. No retry compaction event exists; retry's highest observed single-response input is 172,072 tokens (below configured 256,000; compact threshold in checkpoints is 183,808). A claim that retry compaction or continuation was tested would be unsupported. All three manifests have zero `continuation_link` records; initial anchors show null handoff notes/continuation. 

## Retrieval and context use

In the retry, agents issued ten `search_library_source` calls. Six returned hits, including three `gronwall`/`Gronwall` searches returning 40 hits each; four exact-name guesses returned zero. One `lookup_library_source` opened the 32,660-character serialized visible output for `Mathlib/Analysis/Calculus/Deriv/MeanValue.lean` (`call_H6YCyPJq12Pu5jUP58QHYIux`, session `cf254fc1-d573-4470-b0be-a1c1f3f44b4a`). The one retry `search_knowledge` (`call_YenICO2CP8qKqoUPVoxM5LV6`, 23:52:37 UTC, `tool_completed` event `b93d66bc-8b95-49ef-bdc5-782cbc8544b9`) returned `items: []`, `reason_code: no_lexical...`; calibration and first cooperative searches also returned no items. The library source index demonstrably supplied usable names, while the separate knowledge bank contributed no records in these runs. Empty bank results alone do not prove a retrieval defect or absent prior knowledge. Repeated broad Gronwall searches and full-file lookup are modest context overhead, not the principal cost.

Four artifacts were read by multiple peers: `afa8dd7a-0792-4a82-828f-1156d1746423`, `e72d1474-e3e9-42be-926f-0227c485c841`, `79fcab46-1277-4fc6-94e1-105529469182` three times each, and `d5595842-7302-46d2-b1b8-53549f82563f` twice. This is an expected envelope guard and recovery, not lost memory. First cooperative and calibration exports have nine and two `checkpoint` artifacts, respectively. No continuation/handoff consumed these artifacts in the retry, so their effectiveness after a session restart remains unmeasured.

## Tool friction and recovery

The retry had 338 model responses and 332 completed tool events. Visible function calls included 97 `run_lean_scratch`, 72 `run_command`, 63 `send_message`, 19 `store_artifact`, and 18 `read_artifact`. Many Lean nonzero exits were ordinary iterative proof debugging, not infrastructure failure. Two retry agents tried `lake` through `bash -lc` and got exit 127 (`call_LMioXqAn3ykBHq6GofG6lqAE`, `call_JP2OzJOnfu3RTXa1xlhZF7xi`); both then used `/opt/lean/bin/lake`. The main root also tried `scratch/Full.lean` from the wrong working directory (`call_QGg0ZNATihcdPLXyl7oVFPvN`, completed 23:58:59 UTC, event `4438a94b-bce6-4ed5-b9ee-4ff57d1ce42c`); stderr reported both `No such file or directory` for the relative path and `lake: command not found` under `bash -lc`. Its exit 127 reflects the latter command failure. It subsequently used `/work/scratch/Full.lean` (`call_Ttv7dcZwa5Seg780sVD4tEim`). Similar `lake: command not found` path friction occurred in calibration and first cooperative runs, so the environment guidance/path default remains a small recurrent friction source. It did not block the retry proof.

The retry's eight explicit tool errors (two `inspect_verification` NOT_FOUND, two `MESSAGE_ATTACHMENT_INACCESSIBLE`, one `INVALID_CURSOR`, one `SCIENTIFIC_CORE_TOO_LARGE`, one `CANDIDATE_FORMAT`, one `send_message` NOT_FOUND) were recovered or nonterminal. The retry proof was independently verified and the final root message cited receipt `9c834332-48e9-4e75-947e-9aaa3e5b13b4`. `inspect_verification` NOT_FOUND in a peer session (`call_CQjuTKA1CsSfPie2fONH2gtq`) indicates project or actor scope of receipt visibility rather than failed verification; the manifest contains the approved review and verified claim. The first cooperative run additionally shows workspace reconciliation errors in session `f3d12baf...` (`call_hqAjUd4DfWEXfBag12x8Fzos` and `call_yNUZ2EXzcLHRlKuTqtJjGkFN`), followed by task failure/uncertainty in that earlier campaign. Those errors did not recur in the retry.

One avoidable coordination cost is visible in session `00ea3537...`: after its mathematical contribution was shared, it issued seven `run_command` sleep calls (`call_v8SF...`, `call_SbA6...`, `call_DJNV...`, `call_7u6...`, `call_KeVt...`, `call_1Jlk...`, `call_Ccxc...`) totaling requested sleeps of 160 seconds, interleaved with mailbox/discussion/status checks. A wait primitive or terminal child status subscription could avoid polling model turns, though the observed incremental provider cost for those turns is not isolated. The root used detached delegation and peers did deliver useful Lean sublemmas, so this is a narrow efficiency finding.

## Limits

Call times in this report are `runtime_event` completion times unless explicitly labeled otherwise; a provider response `created_at` is earlier than tool dispatch and must not be read as a tool completion time. The manifests expose only exported artifacts and final visible checkpoints, not a causal profile of server storage IO, VM memory, provider latency, or post-run handoff. Immutable checkpoint payload byte totals must not be described as network traffic or RSS. The final states can be verified against their SHA named blobs and event IDs above; encrypted provider reasoning content was neither read nor reconstructed. No implementation change was made.
