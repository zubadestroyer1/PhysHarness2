# Continuation design audit (read-only; 2026-09-23)

## Current seams

- `ResponsesRuntime._loop` (`execution/responses.py`) sends stateless `responses.create(..., store=False, include=["reasoning.encrypted_content"])` requests from `native_state["input"]`; full provider responses are retained in `native_state["responses"]`, and tool results are cached by `session_id:call_id`. A pending operation blocks automatic resume. The checkpoint digest covers the full session and native state.
- `RuntimeLimits.max_total_tokens` is presently both a cumulative charged-token limit and an effective context ceiling: preflight subtracts the *current input count* from cumulative remaining. This prevents long sessions even after context is compacted. `max_turns` is similarly per native session, while the experiment ledger supplies the true cross-session cost/token envelope.
- `CanonicalRuntimeStore` writes immutable `native_checkpoint` artifacts and a fenced current session record. `ResearchTaskExecutor.execute` rejects any prior session for a task before acquiring a lease, then always starts a new runtime. A successor path therefore needs an explicit, durable handoff state; merely removing that guard risks duplicate paid requests.
- `PortableMemory.checkpoint`/`restore` and `restart_brief` are canonical scientific memory; they do not replace native encrypted reasoning state. `restart_brief` currently returns every artifact, message, claim, receipt, and task, so its direct inclusion in every fresh prompt can grow without bound.

## Native compaction interface

The installed SDK is OpenAI Python **2.54.0**. Its `responses.create` request accepts `context_management=[{"type": "compaction", "compact_threshold": int}]`. The response output union includes `ResponseCompactionItem` (`type="compaction"`, `id`, `encrypted_content`). The separate `responses.compact` endpoint has its own billable `usage`; avoid it initially because the existing generation reservation already accounts for inline compaction usage. Neither endpoint was called in this audit.

Add `RuntimeLimits.max_context_tokens: int | None` and a validated runtime setting such as `compact_threshold_tokens: int | None` (ideally `0 < threshold < max_context_tokens - max_output_tokens`). Keep `max_total_tokens` as a cumulative per-session guard, and keep the experiment ledger as the aggregate hard guard. Compute `input_count = responses.input_tokens.count(...)` on the **active** input. Reserve output from `max_total_tokens - session.input_tokens - session.output_tokens - input_count` exactly as today, then independently reject an input that already violates the active context ceiling. Pass `context_management` on create at a threshold below the ceiling, with room for output. Model compatibility remains provider-authoritative, so preflight should expose an unsupported-field failure without retrying as an un-compacted request.

After `response.usage` is durably captured and its reservation settled, append exact native output including encrypted reasoning and compaction items. Retain the full immutable response history, `tool_results`, operation IDs, and ledger records. Only prune **active** `state["input"]` at a safe boundary after all function calls in that response have their outputs durably saved. Select the latest compaction item as the new prefix and retain every subsequent output item and matching function-call output in order. Never prune a pending tool call, unmatched tool output, latest reasoning/compaction item, or the only copy of an unacknowledged result. Record `active_input_epoch`, compaction item ID, source response ID, and previous checkpoint digest in native state for recovery; verify the compacted input by a fresh `input_tokens.count` before another generation. The full `responses` and `tool_results` remain an audit/replay archive even when active input shrinks. A compaction item is opaque provider memory, never a scientific proof or review.

Suggested narrow helpers: `RuntimeLimits.max_context_tokens`; `ResponsesRuntime._preflight_generation(session, state) -> (input_count, output_reservation)`; `_commit_response_and_usage(...)`; `_settle_tool_calls(...)`; `_advance_active_input_after_compaction(state, response_id)`. Preserve the existing generation ID and reservation/usage event order. Add context metadata to `generation_started`/checkpoint for diagnosis without treating token count preflight as billable usage.

## Durable fresh handoff

Use the existing task and branch IDs and experiment envelope. A handoff should create a **new native session ID** after the previous session has reached a clean, fully settled boundary. This avoids changing checkpoint identity or rewinding it. Define a fenced `task.handoff` command that atomically records the source session ID/checkpoint digest, target/branch/task IDs, portable checkpoint or canonical restart reference, cumulative task usage/turns, reason, and next session ordinal; releases the current lease and returns the task to `queued` (or a dedicated `handoff_ready` runnable state). Idempotency key should derive from task ID and source checkpoint digest. The prior native session remains immutable and marked terminal for handoff. The successor lease owns the new session; `CanonicalRuntimeStore` should refuse a new session unless it matches the task's recorded next ordinal and predecessor digest, while still rejecting ambiguous or uncertain prior operations. Fencing must cover the handoff command and the first successor checkpoint.

`ResearchTaskExecutor.execute` can then distinguish: no prior session -> start; clean recorded handoff -> build a fresh prompt from a **bounded** restart brief plus attributed portable memory, create a new native session; any other prior session -> `RECOVERY_RECONCILIATION_REQUIRED`. Do not use `continue_session` with a completed old checkpoint for a fresh handoff. Keep per-session limits finite and expose separate task or experiment cumulative caps; a successor must not reset the canonical cost/token ledger. If a generation, tool call, usage settlement, workspace cleanup, or checkpoint save is uncertain, block handoff until explicit reconciliation. A `handoff_requested` result from the runtime at a safe preflight boundary is preferable to turning limit exhaustion into `blocked` task failure. The runner must count handoffs as one logical task, not as fresh delegated tasks consuming `max_tasks`, and avoid a tight no-progress handoff loop.

For the proposed callback design, add `boundary_hook: Callable[[RuntimeCheckpoint], Awaitable[ContinuationRequest | None]]` to the runtime constructor. Invoke it with a detached checkpoint only after usage event settlement, every output tool result save, and active-input pruning save. The hook may inspect canonical handoff intent but must not mutate native state. Validate `ContinuationRequest` as a small structure (`reason`, optional canonical intent ID); create a final source checkpoint with `status="handed_off"`, and return `RuntimeResult(..., continuation={"reason", "source_session_id", "source_checkpoint_digest", "active_input_epoch", "compaction_item_id", "turns", "input_tokens", "output_tokens"}, output_text="")`. Add `"handed_off"` to `RuntimeSession.status` and reject `resume`/`continue_session` for it. Existing `"interrupted"` is unsafe here because `resume()` deliberately reopens it. The worker must verify the handoff result against the saved checkpoint, then commit the fenced canonical intent. A crash after the source checkpoint but before that commit is a known-safe reconciliation case, not permission to start a successor automatically.

Proposed entry points: `ResponsesRuntime.start(..., handoff_source: str | None = None)` only for provenance; `CollaborationMixin.handoff_task(task_id, holder, fence, source_checkpoint_digest, handoff_artifact_id, actor, key)`; `ResearchTaskExecutor._select_start_mode(task, sessions)`; `CanonicalRuntimeStore.save` enforces recorded session ordinal/predecessor. The handoff artifact should contain a bounded prompt view and canonical IDs/digests, not copied raw native state. `PortableMemory.restore` and canonical records provide target and evidence identity. Existing `fork_branch` and `delegate` tools remain the way to create independent child work under the same experiment envelope.

## Hazards and qualification tests

1. Inline compaction may appear in an output that also contains tool calls. Test exact item ordering and no pruning until each matching tool result is settled; restart from every checkpoint between response receipt, usage event, tool dispatch, and pruning. Preserve `reasoning.encrypted_content`, compaction `encrypted_content`, full response history, and tool idempotency cache.
2. Mock SDK 2.54 requests/responses to prove `context_management` is sent, active input falls after a compaction item, cumulative counters only rise, and a large active input is rejected before `responses.create`. Test provider response with missing usage remains uncertain and does not prune.
3. Exercise context cap and aggregate budget independently: a compacted 100-turn session can proceed while charged-token budget remains; an exhausted cumulative/experiment budget still stops even with tiny active context. Verify reservation amount bounds create output and inline compaction usage is settled from authoritative `response.usage`.
4. Crash and race tests: lease loss before/after handoff commit; duplicate handoff command; duplicate worker dispatch; same-task concurrent successor; ambiguous previous session; pending generation/tool operation; unsettled reservation; source checkpoint mismatch; cancellation during first successor preflight. Assert no second paid request unless a fenced handoff is clean and unique.
5. Test bounded restart prompt with many artifacts/messages and retrieval of omitted canonical IDs. Ensure unverified summaries remain attributed; accepted receipts and target digest survive handoff. Test child delegation and branch selection still respect the shared experiment envelope.

File ownership suggestion: runtime agent owns `execution/responses.py`, `execution/types.py`, and `tests/test_execution_responses.py`; worker/durability agent owns `orchestration/research_worker.py`, `collaboration.py`, and corresponding orchestration/integration tests; memory agent owns `memory.py`, bounded `restart_brief`/query APIs, and memory tests. `run_control.py` plus `execution/parameters.py` should be reviewed together for plan validation, with a single coordinator reconciling the shared `RuntimeLimits` contract and final qualification. Avoid simultaneous edits to `research_worker.py` and `collaboration.py` across agents because lease and session ordering span both.
