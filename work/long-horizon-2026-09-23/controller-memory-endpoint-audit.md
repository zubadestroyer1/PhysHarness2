# Controller and memory endpoint audit

Scope: read-only inspection of `orchestration/research_worker.py` and `continuation.py` after the memory additions, plus isolated tests. No private pilot state, model, VM, credential, or provider call was used.

The worker registers `checkpoint_research_notes`, `working_context`/`restart_brief`, `read_scientific_record`, `history_page`, `index_page`, `research_graph_page`, and `read_artifact_chunk`. Fresh worker prompts and native compaction anchors contain canonical bounded working context and same-task handoff notes. The continuation authority selects the latest task-bound portable checkpoint, records its artifact ID and SHA-256 in the ticket, and the worker compares the returned handoff note identity against that ticket before resuming. This is an identity check; mathematical statements in notes remain explicitly unverified.

The additive notes checkpoint is needed for large histories: legacy `portable-context.v1` still embeds every open task, open claim, and failed attempt and can exceed a small envelope. The new `research-notes.v1` keeps only exact target/review/environment hashes, current-task and selected-evidence references, streaming obligation fingerprints, and attributed notes. A 160-task service test shows legacy v1 failing at 8 KiB while new notes issue and hand off within 8 KiB. Stale task or selected evidence changes retain attributed text but mark it stale and remove changed evidence references. A same-count obligation swap is detected by fingerprints.

Remaining integration detail: continuation checkpoint selection currently orders only by `created_at`, whereas `handoff_notes` orders by `created_at` and ID. Equal timestamps could select different checkpoints, causing a safe but unnecessary `CONTINUATION_STALE` failure. The controller author has been asked to align ordering. Likewise, worker tool schemas should expose a page `limit` so an agent can retry after `CONTEXT_ENVELOPE_EXCEEDED` on a 50-reference history/index page. The memory methods already accept the limit and now cap output bytes.

The external HTTP/client/MCP surface is not yet feature-complete. `api.py` has legacy checkpoint, history, working context, index, record, and artifact chunk routes, but no research graph route, notes checkpoint route, or handoff notes route. `client.py` and `mcp_server.py` likewise lack graph and notes methods; MCP also lacks history/index paging. The API's history limit currently accepts 500 while memory enforces 100. The controller author owns these files and has been sent the exact additions with `Actor`/`Key` authentication and canonical branch/task scoping requirements.

Bounded page and artifact reads are response envelopes, not a proof of bounded internal memory consumption. The artifact store verifies and loads a whole artifact before returning a 16 KiB base64 chunk. For very large artifacts, range-reading and streaming hash validation would require a separate storage change. This does not disclose private/native artifacts and is not a blocker for the two-target qualification, but should be measured before advertising arbitrarily large artifact support.

The controller test for a one-slot parent yielding to a child and then resuming exercises the notes tool and sees the unverified note in the successor prompt. It is a local mocked-provider integration test, not evidence of a live mathematical result or natural long-horizon performance.
