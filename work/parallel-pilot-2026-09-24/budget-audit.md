# Budget and horizon audit (read-only)

Scope: `src/physharness/execution/{responses,context_policy,parameters,types}.py`, `orchestration/research_worker.py`, `run_control.py`, `service.py`, the prepared collaboration proposal and saved model prices. No paid calls or production edits were made.

## Priority findings

1. **The proposed two-hour window is the decisive artificial stop.** `experiment-proposal.json` sets `max_runtime_seconds_per_experiment=7200` and `supervisor_timeout_seconds=7200`. The team runner cancels active tasks at its timeout (`research_worker.py` around 1674, 1630), while every new worker/model reservation calls `service._active`, which refuses allocation after the experiment runtime (`service.py` around 850). A resumed supervisor cannot recover the experiment after its deadline. Set the experiment deadline to a high finite operator value, e.g. 7 days (`604800` seconds), and launch the supervisor in finite 24-hour slices (`86400`, the manifest maximum), with explicit restart against canonical task state if still active. The first supervisor slice must end before the experiment deadline; retaining the original experiment start and $25 ledger is essential. If unattended multi-day operation is required, a finite-slice restart controller needs implementation and testing; merely increasing the experiment deadline is insufficient.

2. **The 128-turn session cap causes frequent handoffs and may become a failure at a boundary.** `RuntimeLimits.max_turns` is per native session (maximum allowed value 1000); it is not a lifetime budget. `boundary_hook` requests a handoff at `max_turns-1`, and the next session can continue the same task. Increase the configured cap to `1000` for this pilot and keep `max_total_tokens=null`. This avoids a cumulative artificial token cutoff while retaining provider/session safety. A numeric `max_total_tokens` persists across compaction and continuation through cumulative offsets; the default `32768` is unsuitable. Existing prepared proposal correctly says `max_cumulative_tokens=null`; actual launch plans must explicitly translate it to `runtime_limits.max_total_tokens=null` rather than omit the field.

3. **Conservative full-window input reservations can strand usable dollars.** With compaction enabled, each generation reserves the entire `max_context_tokens` as input (`responses.py` around 521), plus `max_output_tokens` as output. At 256,000 context and 64,000 output with the safe $2.50/M input rate, the hold is `$0.640 + $0.640 = $1.280` per response, `$2.560` for two simultaneous workers. If the experiment has less than `$1.280` unspent/unreserved, a request is rejected even when token count and likely output are small; a second worker can be rejected transiently while the first holds a reservation. `ResearchTaskExecutor` converts `BUDGET_EXCEEDED` into a failed task; `ResearchTeamRunner` records the failure as a blocked outcome. It does not wait for the sibling hold to settle or reduce the reservation. Minimal remedy: distinguish temporary reservation contention from true exhausted balance, retry the former after settlement; calculate a safe output cap from available dollars before reserving a request (and pass the same cap to Responses) to use most remaining dollars. If the input full-window hold alone exceeds remaining balance, use a deliberately smaller per-request context limit at a safe handoff or report that the strict full-window hold makes the rest unavailable. Never send an unreserved request.

4. **Settlement trusts actual cost beyond the original reservation.** `service.settle_resources` adds `actual` to `budget.spent` without checking `actual <= reservation.reserved` or `budget.spent + reserved + actual <= max_cost`. Normal Responses usage should fit the reserved token quantities, and `responses.py` detects a usage overflow, but that check occurs *after* the `usage` event has settled and spent the charge. Generic settlements can also exceed reserves. Reject an over-reserve settlement or move it to explicit uncertain reconciliation, retaining the provider usage evidence. This is a potential ledger overspend gap, not evidence of an observed paid overspend.

5. **The saved pricing misses cache-write charges.** `ModelPrice.cost` prices all input tokens at one rate, and the historical `gpt-6-sol` file sets that rate to $2/M. Current [OpenAI prompt-caching documentation](https://developers.openai.com/api/docs/guides/prompt-caching) says Responses usage includes `input_tokens_details.cache_write_tokens` and `cached_tokens`; writes cost 1.25 times ordinary input ($2.50/M for this model). Thus `$2/M` can under-reserve and under-settle by $0.50 per million write tokens. Before any paid launch, use `$2.50/M` as the conservative input price and label the ledger as a ceiling estimate rather than exact billed cost. A later exact-cost implementation can reserve at $2.50/M and settle using `ordinary=input-cached-writes` at $2, reads at $0.20, writes at $2.50, verifying the detail counts. See [official price table](https://developers.openai.com/api/docs/pricing).

6. **The four $25 envelopes have no durable global $100 ledger.** Each experiment has its own row and transactional reservation lock. Sequential launch of exactly four experiments with envelopes of `$25` yields at most `$100` by operator discipline, provided all charge classes are included. A fifth launch or larger envelope is not rejected by an aggregate campaign ceiling. Record and gate run count/aggregate envelope in the pilot launcher if a hard $100 cap is required.

## Exact recommended launch values and price math

Use `gpt-6-sol`, `reasoning.effort=high`, `max_context_tokens=256000`, `max_output_tokens=64000`, `max_total_tokens=null`, `max_turns=1000`, `timeout_seconds=86400` per native session invocation, `max_runtime_seconds=604800` per experiment, and supervisor `timeout_seconds=86400` per slice. The runtime session timer covers the entire `_run` loop, not one provider response. The provider's stated model ceiling is 1,050,000 context and 128,000 output; 64,000 is an operating allowance, not a lifetime cap. With a 256,000 context window, preflight requires `input + 64,000 <= 256,000`, so actual input is at most 192,000 per request, below the 272,000-input long-context price threshold. The research compaction threshold becomes `min(3/4 * 256000, 256000 - 64000 - 8192) = 184000`. At safe ceiling prices ($2.50/M input, $10/M output), the full hold is $1.280/request. Actual max usage under preflight costs at most $1.120; the additional $0.160 is temporary reservation conservatism. The present 128,000/16,384 settings would hold `$0.483840` per response at safe rates and permit at most 111,616 input tokens. Raising output to 128,000 in a 256,000 context would reduce permissible input to 128,000 and hold `$1.920`; 64,000 is more balanced for research.

The fixed input hold can reserve more than actual input, but transaction locking in `reserve_resources` prevents concurrent workers from jointly reserving beyond the experiment $25 when the configured price is a true upper bound. Each of four experiments should have `max_cost_usd="25"`, `max_concurrency=2`, and `max_tokens=null`; no shared cumulative token cap. Revalidate model prices at launch, including the provider's long-context threshold and service tier. Saved `.state/runs/first-pilot/model-prices.json` contains historical ordinary standard rates, which are too low for a hard spending ceiling on cache-write models. Do not rely on cached-token discounts to make the safety calculation.

## Recovery and limit distinctions

The per-response `max_output_tokens` is sent to `responses.create`; the `max_context_tokens` bounds active input plus reserved output; `max_total_tokens` counts cumulative native-session and continuation usage; `max_turns` counts provider responses within a session; `timeout_seconds` covers one `_run`; `TeamRunManifest.timeout_seconds` covers one supervisor invocation; `ResourceEnvelope.max_runtime_seconds` is the absolute experiment reservation deadline. Provider compaction prunes active context but never resets experiment spend or cumulative counters. The worker preserves an unknown-use response and leaves its reservation held until reconciliation; avoid blind retry on uncertain usage. The proposed max tasks (16) and verification count (default 8 unless overridden) are additional finite throughput gates if the research group delegates extensively.
