# Independent launch audit (read-only)

Reviewed the current local Docker capacity, workbench preflight, budget reservation and settlement, Responses loop, and one-shot pilot launcher against the parallel-pilot briefs. No credentials, paid calls, VM starts, or production edits. Prior focused checks already recorded in `capacity-report.md`, `preflight-report.md`, and `capacity-preflight-tests.log`; I did not rerun them.

## Actionable findings

1. **High — $100 spending guard depends on an unchecked price file.** `pilot_ops.py:104` loads `model_prices_file` into Settings, and `validate_arms` checks model ID and runtime but does not require conservative `gpt-6-sol` rates. `run_preflight` checks only that `ModelPrice` parses. The current `.state/parallel-pilot-2026-09-24/prices.json` has the correct conservative `$2.50/M` input and `$10/M` output rates; a stale replacement at `$2/M` could undercount cache writes, so the code does not enforce the real $100 bound. Before launch, validate exact `gpt-6-sol` price entries `input_usd_per_million >= 2.50` and `output_usd_per_million >= 10.00`, standard tier only, and a source/current-price attestation. The conservative ledger is then an upper estimate, not actual billed cost. No global aggregate row exists, so launcher config and operator sequencing remain the $100 control.

2. **High — 24-hour experiment, session, and supervisor limits coincide.** `pilot_ops.py:138-146` requires `max_runtime_seconds=86400`, `runtime_limits.timeout_seconds=86400`; `run_one` also gives `TeamRunManifest.timeout_seconds=86400` at line 284. The experiment's absolute clock starts at `transition_experiment` before seeding, preflight and worker startup. The supervisor's clock starts later and may cancel live requests just as the experiment refuses new reservations (`service._active`). A restarted controller cannot extend the original experiment. This is a finite safety limit but remains an artificial stop before the $24.95 envelope is used, and cancellation may leave uncertain model charges. Prefer a longer finite experiment envelope and shorter bounded supervisor slices with an explicit operator restart path on canonical records; at minimum leave several minutes between session/supervisor and experiment deadlines and state this pilot's 24-hour maximum plainly.

3. **Medium — the full-window reservation strands the last $1.28 of each arm.** The Responses loop reserves 256,000 input and 64,000 output tokens per generation with compaction. At safe launch rates this holds `$1.28` per request even if active input is much smaller. `_reserve_model_with_wait` now correctly waits for a settled sibling hold, but once unreserved balance falls below `$1.28` it returns `BUDGET_EXCEEDED` without shrinking request output or context. One failed task can make `ResearchTeamRunner` return blocked, ending the arm with meaningful budget left. This is conservative, but the pilot brief's “research lasts as needed within budget” is not fully met. A later bounded output reservation and safe context handoff would use more of the approved budget; do not issue an unreserved request.

4. **Medium — preflight memory is a capacity estimate, not current free memory.** `workspace_tools.py` subtracts 2 GiB per labeled running workbench from Docker `MemTotal`, then compares the 14 GiB requirement for two workers, verifier and headroom. It does not read host or VM current memory pressure, so a 16 GiB daemon with large non-Docker processes can pass yet later OOM. The dedicated-daemon check blocks unrelated running containers, which substantially narrows the gap. Record an actual VM free-memory check immediately before live launch, or clearly treat it as an observed operational risk. Docker's atomic admission remains authoritative for workspace count.

5. **Medium — preflight is not an integrated launch gate for `ResearchTeamRunner` itself.** CLI and `pilot_ops` call `run_preflight` with requested concurrency; direct use of `ResearchTeamRunner.run` checks only the experiment's concurrency envelope. Another caller can bypass memory/capacity preflight, although the provider still refuses a third workspace. If this runner is used as a public live-launch path, make the preflight an enforced prerequisite there or constrain all live launch entry points. For this four-arm launcher, the explicit call is present.

6. **Low — public status may disclose experiment and receipt identifiers.** `pilot_ops.snapshot` allowlists fields and excludes proof sources, prompts, messages and credentials. It writes experiment ID and receipt IDs to the configured `status_file`; if that file is user-visible beyond the operator, these are metadata disclosures. Put the status file under the private directory or constrain its parent and permissions. `atomic_json` itself writes mode 0600 safely.

## Positive controls observed

- The Docker provider uses a stable `/tmp` flock keyed by the dedicated socket, counts active labeled workbenches under that lock, rejects mismatched capacity labels and names each container uniquely. It caps each worker at 2 GiB/2 CPUs with no network, read-only filesystem, nonroot user and no host bind mounts.
- `run_preflight` receives the actual requested concurrency from both CLI and pilot launcher and blocks if capacity/memory checks fail. The pilot calls it before experiment transition, seeding or model work.
- `reserve_resources` transactionally locks the experiment budget and accounts for spent plus outstanding holds. The new waiting path distinguishes sibling holds from exhausted spend and refuses uncertain reservations. Over-reserve settlement retains actual usage, flags `budget_reconciliation_required`, and blocks further allocation; this is a sound response to a charge already incurred.
- Unknown provider usage or request state stays uncertain, preventing automatic replay. Canonical task leases/fences and session checkpoints are consulted on worker recovery. The pilot launcher starts only created arms and fails closed on a blocked result or uncertain ledger.

This audit did not run the independent verifier/comparator, reproduce real concurrent model calls, or assess scientific correctness of target review. Those require the root's final qualification gate.

## Operator disposition and 64K response cap

The root operator accepts a finite 24-hour pilot rather than a multi-day long-horizon qualification, will monitor near its deadline, and accepts the documented $1.28 reservation floor. The direct runner is a lower-level interface; the qualified four-arm path is the guarded launcher. These decisions narrow findings 2, 3 and 5 to stated pilot limitations rather than launch blockers. The current price JSON has the safe rates; finding 1 remains a code-enforcement issue until the launch helper validates them.

`ResponsesRuntime` passes the reserved 64,000 output-token cap to the provider. If the provider returns `status=incomplete`, the runtime saves the native response, emits usage to settle the reservation, verifies usage did not exceed the hold, and then raises `PROVIDER_INCOMPLETE`. This is financially safe but not an automatic continuation. The private checkpoint retains `incomplete_details.reason`; neither the failure code nor public status distinguishes `max_output_tokens` from other incomplete causes. Count exact `max_output_tokens` reasons from private checkpoints in the final report rather than treating every `PROVIDER_INCOMPLETE` as a cap hit.

Final read-only launcher review: the helper now calls `validate_prices` and requires finite `gpt-6-sol` input at least $2.50/M, output at least $10/M and a nonempty source. `validate_arms` requires the exact `{"reasoning":{"effort":"high"}}` parameter object, excluding a fast tier override, plus the expected context/output/turn limits and $24.95 arm ceiling. The present price file matches those requirements. The allowlisted public `status.json` sits under the pilot `.state` directory and is written mode 0600; private result/native files remain in the configured private directory. Finding 1 is resolved for this launcher; finding 6 is a low-priority placement note rather than an observed disclosure.
