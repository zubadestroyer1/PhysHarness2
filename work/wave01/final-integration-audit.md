## Finding

### P2 — Registry startup cannot verify the raw profile-source pin

`src/physharness/bootstrap.py:55-74` reads the configured resource file and checks its actual SHA-256 and canonical digest in single-bundle mode. In contrast, `src/physharness/verification/registry.py:44-67` accepts a `ComparatorConfig` whose `resource_profile_source_sha256` comes from JSON. `_PinnedRunner._bundle` at `src/physharness/verification/boundary.py:399-407` compares that declared value to the qualification's declared value, but there is no path or byte read for the registry entry's source file. `docs/VERIFICATION.md:160-167` puts the exact-source hashing obligation on the operator; the runtime cannot check it.

Focused host reproduction: using the existing `tests/test_verification.py:35-90` fixture, change both the registry config and qualification's raw-source hash to `f` repeated 64 times while leaving canonical resources unchanged, then load the JSON through `RegistryDocument.model_validate_json` and construct `VerifierRegistry`. `registry.preflight(request).code` is `configured_unprobed`, although no resource-profile file exists in the temporary bundle. No Docker or candidate ran. This demonstrates the unchecked source assertion; it is not a fabricated-proof or approval exploit, because the qualification object itself is operator-owned and still needs human review.

Smallest fix: give each registry entry an explicit resource-profile file path and, during `VerifierRegistry.from_file`, read bounded non-symlink bytes, parse and hash them, and compare both actual raw and canonical digests with the entry and qualification. Preserve the present policy-source check. Add one registry startup regression where a byte-only profile change leaves canonical values equal but fails before a verifier is exposed. If the intentional registry contract is instead to trust an external profile-source attestation, narrow the documented startup guarantee explicitly; that weaker contract does not meet the exact-source requirement in this brief.
